Methods

The question. This project has exactly one content-extraction path — a BeautifulSoup pre-clean feeding trafilatura.extract(…, favor_precision=True), wrapped in a prose→listing→document→render fallback ladder. It was never measured against an alternative, and there is no automatic metric for extraction quality that does not need gold annotations. So the metric here is human judgement over blind pairwise comparisons.

Fetch once, extract many. Each URL was fetched exactly once and snapshotted; every entrant then ran against those identical bytes. Re-fetching per entrant would give each a different document (A/B tests, rotating banners, edits) and any quality difference would be confounded by snapshot luck. It also means the arena needs no network at all.

Entrant = (input variant, extractor). Keeping the input explicit makes the raw-vs-rendered axis votable rather than a hidden constant. Two snapshot variants exist per page: raw.html (httpx GET) and rendered.html (Playwright, networkidle, falling back to domcontentloaded plus a grace period on ad-heavy pages that never settle).

Blinding. Columns are labelled A and B, left/right assignment is randomised per matchup, and identity is revealed only after the vote is committed. entrant_a is stored as the left column, so position bias stays measurable afterwards — it is reported below.

What is judged. Raw output strings in a <pre>, because that string is what lands in a corpus: stray ](#) links, duplicated navigation and broken tables must be visible rather than styled away. Note an asymmetry: ours, trafilatura* and scrapling-md emit Markdown while the rest emit plain text, since that is all they produce. Stock trafilatura is deliberately configured to Markdown so the ours vs trafilatura matchup isolates our wrapper rather than a formatting difference.

Active sampling. Pairs are drawn with probability proportional to p(1-p) / sqrt(1 + n_ij), where p is the ELO-expected win probability. p(1-p) peaks for evenly-matched pairs and decays as one side dominates, so first-versus-last stops being sampled once it is settled; the n_ij term spreads coverage. Draws are proportional rather than argmax, plus a 10% uniform-random floor so early noise cannot freeze the ordering. Pages are chosen round-robin across the four buckets so per-bucket ratings stay balanced at any stopping point.

Auto-draws. Byte-identical outputs are recorded as draws and never shown. This is what makes the raw-vs-rendered axis affordable: on a static page an extractor and its @rendered twin agree exactly, so the pairing only reaches the reviewer when rendering actually changed something. Auto-draws are tagged and counted separately from judged draws.

Timing. One discarded warmup call, then the median of three timed calls, single-threaded, all entrants in one run on one machine. The warmup matters: resiliparse is Cython and goose3 lazily loads stopword data, so a cold first call would measure import cost. input_ms (the cost of producing that entrant's input) is charged to the entrant, because needing a headless browser is a real cost rather than a free precondition.

Ratings. Online ELO (K=24, start 1500, draw=½) drives the live view. The report leads with Bradley-Terry MLE plus percentile-bootstrap 95% intervals, because sequential ELO is order-dependent — the same votes in a different sequence give different numbers, which matters at these vote counts. Bradley-Terry is order-independent and yields intervals, so overlapping bars can be read honestly as “indistinguishable”. Draws count as half a win to each side (Rao-Kupper simplification). Votes are stored append-only, so every rating is recomputable from scratch.

Defects found and fixed during the build

These were found by auditing the harness rather than trusting it, and each one would have corrupted a headline number. They are recorded because anyone reproducing this needs to know the traps.

  • trafilatura's deduplication cache silently gutted our own output. Our pipeline passes deduplicate=True, which drives a process-global LRU cache. Because the timing protocol calls each entrant several times per page, the 4th call onward returned progressively less text, and the runner stored the last call. On one page that meant 17,028 characters collapsing to 618 — a 96% loss — and it leaked across entrants, since ours and ours@raw-only run back to back over the same HTML. Every ours output was affected (median −8%, worst −96%). Fixed by clearing that cache before every call and storing the first timed result; outputs are now verified byte-stable across repeats. Note the consequence: ours is measured on a cold cache, so this comparison does not model the cross-page boilerplate suppression a warm cache gives in production.
  • goose3 was being treated unfairly by our adapter. It reported 36 empty pages; 19 of those were an artifact. goose3's post_cleanup() keeps a hardcoded tag whitelist and deletes all other children of the article node, and modern Wikipedia is served as Parsoid HTML wrapping content in <section>. goose3 found the right container and then deleted all of it. Fixed with goose3's own known_context_patterns knob, applied as a retry only when the first pass is empty (applying it unconditionally regresses 16 pages that already work). Empties 36 → 17. The remaining 17 are genuine: goose3 is news-tuned and high-precision/low-recall, and even when rescued it recovers a section rather than the whole article.
  • Three rendered snapshots were anti-bot pages. The raw fetch path screened for Cloudflare and error interstitials; the Playwright path did not. Two 403s and one Cloudflare challenge were stored as valid renders, scored as successful ~190-character extractions, and counted as evidence that rendering changes output — precisely where it had failed. The renderer now applies the same screening and re-uses the URL the raw fetch actually succeeded on.
  • Raw fetch time measured the politeness delay. The per-domain throttle sleep sat inside the timed region, so pages on multi-candidate domains read ~3400 ms against ~150 ms for single-candidate ones. That understated the browser's relative cost several-fold. The throttle is now waited out before the timer starts.
  • Our wikiextractor adapter configured a phantom class. WikiExtractor.py puts wikiextractor/extract/ on sys.path and does from extract import Extractor, importing extract.py a second time under a different module name. Our adapter configured wikiextractor.extract.extract.Extractor — a different class object, invisible to the tool's own logic. Its discard config therefore stayed a literal path string, so every title.lower() in self.discardTemplates test degraded into a substring match against "config/discard_templates.txt": "ca" occurs inside "discard", so any page using a {{ca|1786}} circa template was discarded whole. Beethoven and nl/Amsterdam extracted to zero bytes for that reason alone. Fixed (65,162 and 60,017 chars respectively); 14 votes cast on the stale output were invalidated.
  • The fetcher-divergence count was our regex, not the fetchers. The comparison hashed a regex tag-strip, and <[^>]+> stops at the first > inside an attribute value or comment. Wikipedia's JSON-in-attribute payloads leaked fragments like of the United Nations"}},"i":0}}]}'> into the "visible text" on the raw side only, because Scrapling returns an lxml-reserialized DOM where those attributes are re-quoted. That reported 79 of 93 pages as fetcher disagreements when the fetchers had returned the same content. Both sides are now parsed with lxml, and bodies are persisted so the next suspicious number can be diffed instead of re-fetched.
  • Three wikitext snapshots were redirect stubs. action=raw returns the redirect itself, so wikiextractor was scored on 40–90 byte #REDIRECT documents for three pages, through no fault of its own. Redirects are now followed (the keyword is localised, so the link is matched rather than the keyword).
  • Markdown writer settings were being scored as extractor quality. markdownify defaults to setext headings and backslash-escaping, which put 415 underlines and 384 stray escapes into two entrants' output while trafilatura emits ATX and no escapes. Both are now aligned, so the arena compares extractors rather than Markdown writers.
  • The scrapling-md floor was bloated by our reimplementation. It replicated Scrapling's noise-tag stripping but skipped its hidden-element sanitisation, keeping content the real scrapling extract --md drops (up to +35% on one page). It now calls Scrapling's own converter.
  • Bradley-Terry blew up on sparse data. An undefeated entrant has an unbounded MLE, so a single 1–0 record rated 2817. A symmetric shrinkage prior now keeps early ratings near the mean; it yields to evidence as votes accumulate.
  • The closed leaderboard overlay swallowed every mouse click. display:flex outranks the user-agent stylesheet's [hidden]{{display:none}}, so voting by mouse was impossible until the overlay was explicitly hidden.

Verified clean by the same audits, and worth stating: no adapter touches the network during extraction (checked under a hard socket block, zero connection attempts), so timings and offline reproducibility are sound; there is no minimum-length threshold anywhere that could turn short-but-valid output into “empty” — every empty row is genuinely zero characters; and jusText's byte handling introduces no mojibake (it has the highest diacritic density of any entrant on non-English pages).

Automated judging

A second vote pool is produced by LLM judges, one per matchup, each given a blinded brief and no other context. It exists because Bradley-Terry intervals need hundreds of comparisons before the middle of the field separates, and a human has hours. The brief holds the page metadata, a neutral tag-strip of the same snapshot the entrants were given, and the two outputs labelled 1 and 2 in randomised order; entrant names live in a separate keys directory the judge is never pointed at, and are resolved only when the verdict is recorded. The rubric ranks content coverage first, then boilerplate removal, then markdown-like structure, then token economy, with citation markers and reference lists explicitly minor; a draw is stated to be a legitimate verdict.

It also had to be calibrated against a failure mode that would have inverted the result. Ranking coverage first without qualification rewards the entrant that removes nothing: html-text performs no boilerplate removal at all, so it cannot lose on coverage and would win by default. The rubric therefore treats over-extraction as seriously as under-extraction, states that "kept more text" is not "better", and warns that closely resembling the reference rendering means nothing was removed.

The reference rendering is deliberately not any entrant's output: using one entrant as the yardstick would hand it a perfect coverage score. It is a plain tag-strip, noisy on purpose, and the rubric says so — an output that reproduces its navigation junk scores worse, not better.

The two pools are never merged; see the section above for why, and for the measured correlation between them.

Limitations

  • Blinding is client-side, not server-side. The /api/matchup payload carries the entrant names, because the vote endpoint needs them; the UI shows only A and B and reveals identity after the vote commits. A reviewer who opened the browser console could therefore see which tool produced which column. Nothing enforces that they do not, so the blinding holds by convention rather than by construction.
  • Single reviewer. No inter-rater agreement can be computed, and one person's preferences are baked into the result. The automated pool is a different instrument, not a second rater.
  • Automated judges see excerpts, not whole outputs. Outputs above 10,000 characters are shown as three windows — head, middle and tail — with the true character count stated. That is enough to judge structure and boilerplate, and enough to tell whether the article body survived, but it is weaker than the human's view on the coverage of very long outputs: readability's 178k-char output on one Wikipedia page is shown at 6% of its length. This asymmetry is a reason to treat the human pool as the reference rather than the tiebreaker.
  • The ours adapter deviates slightly. The production ladder calls Playwright live on fallback; here it runs its own decision logic against the cached raw snapshot and, if it declines, the cached rendered snapshot. Same branches, no network.
  • Wikiextractor-V2 is not comparable to the rest. It consumes MediaWiki wikitext, not HTML, so it appears only in the wiki-slice table. It is also AGPL-3.0 (everything else is Apache/MIT/BSD), it only imports on Python ≤3.10 (inline regex global flags), and its --generator mode is broken upstream (collect_pages yields 5-tuples, its own caller unpacks 4). Critically, template expansion — its actual differentiator — is unavailable here, because template definitions live in a dump header and this drives it from single-page action=raw wikitext. Its timings also come from a separate Python 3.10 process and are indicative only.
  • Wikiextractor-V2 drops Spanish articles carrying a hatnote. Its shipped discard_templates.txt lists Otros usos under es, and a template in that list discards the entire document, not just the template. Otros usos is an ordinary "other uses" hatnote, not a disambiguation marker, so España, Madrid and Sagrada Familia all extract to zero bytes — 3 of the 4 Spanish pages in the corpus. Verified as the cause: those three contain the hatnote and the one survivor (Cervantes) does not. This is upstream's config, left unpatched on purpose — editing it would mean measuring our fork rather than the tool. It only became visible once the adapter bug above was fixed, since before that the config never loaded at all. Note also that the config is keyed by language and parsed against the dump's <base> URL, so a multi-language corpus has to reload it per language; a real single-wiki run does this once.
  • Corpus is a snapshot. Fetched on one date; sites change.
  • Output-format asymmetry between Markdown and plain-text entrants may still confer a small presentation advantage despite the raw <pre> default.
  • ours sometimes emits a link list, not prose. Its listing branch fires on a handful of index pages, where a voter is then comparing output format against every other entrant's prose rather than extraction fidelity. That branch is also the only place any entrant receives the page title as an input.
  • Scrapy's median latency is not comparable to the serial clients: it runs a scheduler with concurrency and per-domain politeness, so per-request wall time includes queue wait.
